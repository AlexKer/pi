# Baseten Provider — Design

**Date:** 2026-07-31
**Status:** Approved (pending spec review)
**Branch:** to be created from `main`

## Goal

Add **Baseten** as a built-in model provider available via API key, matching how Together AI and Fireworks are integrated. Users should be able to set `BASETEN_API_KEY` and use Baseten-served models through pi.

## Key decisions

1. **Catalog source: `models.dev`, same as Together/Fireworks.** Baseten's catalog will be extracted from the shared `models.dev` blob (`https://models.dev/api.json`) by `scripts/generate-models.ts`, reading a `data.baseten` / `data["baseten-ai"]` entry — a direct copy of the Together extraction block (`generate-models.ts:1617`).

   **External prerequisite (out of scope for this branch):** Baseten must first be added to the upstream `models.dev` catalog. That contribution is handled in a separate thread; this branch *assumes it is merged*. Until models.dev ships the entry, `baseten.json` will be empty and the provider will resolve no models — this is the same behavior any provider has before its first `npm run generate-models` run.

2. **Default model: `zai-org/GLM-5.2`.** Used in `defaultModelPerProvider` when `--provider baseten` is given without an explicit model.

3. **API: OpenAI-compatible (`openai-completions`) only.** Baseten's inference endpoint is OpenAI-compatible. Single-API shape, like Together (not the multi-API Fireworks shape).

4. **Base URL:** `https://inference.baseten.co/v1` (per the user-provided models endpoint `https://inference.baseten.co/v1/models`).

5. **Env var:** `BASETEN_API_KEY`.

## Architecture

Baseten is an API-key provider with a single OpenAI-compatible API. It mirrors the Together AI integration 1:1. The system already has every abstraction this needs: `createProvider`, `envApiKeyAuth`, `openAICompletionsApi`, the `KnownProvider` union, the `envMap`, and the `models.dev` extraction pipeline.

### Data flow

```
models.dev catalog (external, includes baseten entry)
  → scripts/generate-models.ts  (fetches models.dev blob, extracts data.baseten)
  → packages/ai/src/providers/data/baseten.json  (gitignored, regenerated locally)
  → packages/ai/src/providers/baseten.models.ts  (imports the JSON, flattens catalog)
  → packages/ai/src/providers/baseten.ts         (factory: id, name, baseUrl, auth, models, api)
  → packages/ai/src/providers/all.ts             (registered in builtinProviders())
  → user sets BASETEN_API_KEY → getModel("baseten", "<id>") streams via openai-completions
```

`data/baseten.json` is gitignored (`.gitignore:11`), identical to `data/together.json`. A maintainer runs `npm run generate-models` to populate it; the committed code references it via `baseten.models.ts`.

## Components

### 1. `packages/ai/src/providers/baseten.ts` (new)

Mirrors `together.ts` exactly:

```ts
import { openAICompletionsApi } from "../api/openai-completions.lazy.ts";
import { envApiKeyAuth } from "../auth/helpers.ts";
import { createProvider, type Provider } from "../models.ts";
import { BASETEN_MODELS } from "./baseten.models.ts";

export function basetenProvider(): Provider<"openai-completions"> {
  return createProvider({
    id: "baseten",
    name: "Baseten",
    baseUrl: "https://inference.baseten.co/v1",
    auth: { apiKey: envApiKeyAuth("Baseten API key", ["BASETEN_API_KEY"]) },
    models: Object.values(BASETEN_MODELS),
    api: openAICompletionsApi(),
  });
}
```

### 2. `packages/ai/src/providers/baseten.models.ts` (new)

## Tests

### `packages/ai/test/baseten-models.test.ts` (new)

Modeled on `together-models.test.ts`:
- Model resolution: `getModel("baseten", "<id>")` returns the correct `provider`, `baseUrl`, `api`.
- Env-var detection: set `process.env.BASETEN_API_KEY`, assert `findEnvKeys("baseten")` and `getEnvApiKey("baseten")` return it; unset, assert they don't.

### `packages/ai/test/stream.test.ts` (modified)

Add a `describe.skipIf(!process.env.BASETEN_API_KEY)("Baseten Provider ...")` block with a representative model, mirroring the Together block at line 761. Skipped unless a real key is present, so CI without credentials is unaffected.

### Test footprint rationale

Baseten is **not** added to the full broad matrix (`abort.test.ts`, `overflow.test.ts`, `unicode-surrogate.test.ts`, etc.). Fireworks — the closest analogue — is also absent from that matrix, and Baseten's catalog is account-specific, so picking a stable representative model across the matrix is fragile. The models test + a single stream test matches the Fireworks precedent and is the right footprint for a provider whose model list is not fixed.

## Out of scope

- The upstream `models.dev` contribution (adding the `baseten` entry to that catalog). Tracked separately; this branch assumes it lands.
- A `fetchBasetenModels()` direct-API fallback. Not needed once models.dev is the source.
- Broad-matrix test coverage (see rationale above).
- Any UI / TUI changes — provider display names come from the `name` field in `createProvider()`, so `/login` picks up "Baseten" automatically.

## Risks

- **Empty catalog until models.dev merges.** Until the upstream entry lands and a maintainer runs `npm run generate-models`, `baseten.json` is empty and `--provider baseten` resolves only the default model id (which may not exist on the user's account). This is inherent to the chosen approach and acceptable per the decision.
- **`Record<KnownProvider, string>` completeness.** Forgetting the `model-resolver.ts` entry causes a compile error. Mitigated by it being a hard failure (the build tells us).
- **Default model may not exist on every Baseten account.** `zai-org/GLM-5.2` is the default per the user's decision; users can always pass `--model baseten:<id>` explicitly.
